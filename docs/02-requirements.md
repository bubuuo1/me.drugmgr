# 기능 요구사항

> 이 문서는 검증 가능한 제품 요구사항과 역할 권한의 정본이다. 물리 스키마는 [06 데이터베이스](06-database.md), 구현 완료 여부는 [09 개발 순서와 현황](09-development.md)을 따른다.

## 1. 범위 표기

- **P0**: 데이터 정확성과 온라인 운영을 위해 반드시 갖춰야 하는 기반
- **P1**: P0의 안전·데이터 규칙 위에서 제공하는 일상 사용·관리 기능
- **제외**: P0/P1에서 구현하지 않으며 문서의 향후 기능으로도 약속하지 않는 항목

P0/P1은 요구사항의 범위와 의존성을 나타내며 현재 완료 상태가 아니다. 개발을 병행할 수 있지만 P1 기능도 관련 P0 규칙을 충족해야 하며, 완료 표시는 `09-development.md`에서만 관리한다.

## 2. 공통 요구사항

### 2.1 접근과 데이터

- 사용자는 Google OAuth로 로그인해야 보호된 화면에 접근할 수 있다.
- 인증 callback은 일회용 code를 서버에서 세션으로 교환하고 안전한 쿠키로 유지한다.
- 모든 약·일정·투약 로그·하루 상태는 하나의 복약 공간에 속한다.
- 사용자는 자신이 구성원인 복약 공간만 목록과 데이터를 조회할 수 있다.
- 새 사용자는 비어 있는 개인 복약 공간을 자동으로 받는다.
- 다른 사람의 기록을 보려면 기록 소유자가 공유할 자신의 복약 공간을 직접 선택하고 보호자 권한에 명시적으로 동의해야 한다.
- Supabase가 없거나 연결되지 않으면 앱은 설정 오류를 명확히 표시한다.
- 네트워크 또는 Supabase 요청 실패 시 성공으로 표시하지 않는다.
- 앱 데이터는 브라우저 영구 저장소에 저장하지 않는다.
- 온라인으로 다시 연결되더라도 오프라인 중의 동작을 자동 재생하지 않는다.
- 화면 포커스·표시 상태 복귀 시 접근 가능한 공간과 현재 데이터를 조용히 다시 조회한다. 화면이 계속 보일 때는 권한·초대를 60초마다 경량 확인하고, 현재 기록 전체는 5분마다 안전 재조회한다.
- 백그라운드 재조회는 최초 로딩 화면이나 저장 성공 상태를 만들지 않으며, 구조가 실제로 달라진 서버 응답만 반영한다. 실패한 쓰기를 자동 재전송하거나 로컬 상태와 충돌 병합하지 않는다.
- Web Push를 켠 기기에는 브라우저가 관리하는 알림 권한과 구독이 남는다. 구독은 로그인 사용자와 선택한 복약 공간에 연결되지만 승인 기기 목록으로 사용하지 않는다.

### 2.2 역할과 가족 공유

| 동작 | `owner` | `caregiver` | `viewer` |
|---|:---:|:---:|:---:|
| 공간의 약·일정·기록·구성원 이름과 역할 조회 | O | O | O |
| 약·일정 생성·수정·활성/비활성·삭제 | O | O | - |
| 투약 로그 생성·수정·soft delete·복원 | O | O | - |
| 하루 상태 생성·수정·삭제 | O | O | - |
| 복약 공간 이름 변경 | O | - | - |
| 가족 기록 관리 요청 생성·취소·재발송, 비소유자 구성원 제거 | O | - | - |
| 본인 기기의 공간별 Push 켜기·테스트·끄기 | O | O | O |

보호자의 약 삭제는 soft delete이며 연결 일정을 비활성화한다. 보호자는 공간 이름·구성원·초대를 관리하지 못한다. 조회자는 어떤 쓰기도 할 수 없다. 본인이 참여한 가족 관계의 전환·종료는 일반 구성원 관리가 아니라 동의 부여·철회 동작이므로 아래 제한 RPC를 통해서만 수행한다.

- 소유자는 관리하려는 가족의 이메일을 입력해 가족 기록 관리 요청을 만들고 대기 요청을 취소할 수 있다. 새 관리 요청이 양쪽에 부여하는 역할은 `caregiver`로 고정한다.
- 관리 요청을 만들면 Gmail SMTP를 통해 입력한 주소로 앱 로그인 안내 이메일을 발송하고, 실패한 대기 요청은 다시 발송할 수 있다.
- 요청받은 사용자는 로그인 계정의 확인된 이메일이 요청 이메일과 일치할 때만 수락하거나 거절할 수 있다.
- 수락하려면 요청받은 사용자가 자신이 `owner`인 복약 공간 하나를 직접 선택하고, 요청자와 수신자가 각각 상대 공간의 약·일정·투약 로그·하루 상태를 조회·변경할 수 있다는 양방향 보호자 권한에 명시적으로 동의해야 한다.
- 수락이 완료되면 요청자는 선택된 수신자 공간의 `caregiver`, 수신자는 요청자가 요청을 만든 소유 공간의 `caregiver`가 된다. 서버는 두 공간의 소유권, 확인된 이메일과 요청자의 현재 발신 자격을 같은 트랜잭션에서 다시 검사하고 두 멤버십과 관계 감사 정보를 원자적으로 기록한다.
- 복약 공간과 건강 기록은 관계 수락으로 병합하거나 복제하지 않는다. 사용자는 접근 가능한 기록 대상을 명시적으로 전환해 각 공간을 관리한다.
- 이전 배포에서 만들어진 대기 요청은 새 양방향 동의로 재해석하지 않고 취소한다. 이미 수락된 단방향 관계와 멤버십도 반대 방향 권한을 자동 생성하지 않는다.
- 수락된 가족 관계는 두 참여자의 가족 화면에 표시하고 현재 접근 방향과 공유 공간을 구분한다. 현재 상대 기록을 관리하는 참여자는 자신이 `owner`인 공간 하나를 직접 선택하고 상대가 그 공간의 기록을 보호자로 조회·변경하는 데 별도로 동의해 기존 단방향 관계를 양방향으로 전환할 수 있다.
- 어느 참여자든 활성 가족 관계를 종료할 수 있다. 양방향 관계는 관계가 만든 두 보호자 접근을 함께 제거하고, 기존 단방향 관계는 그 관계가 만든 한 방향 접근만 제거한다. 관계 종료는 저장된 약·일정·투약 로그·하루 상태를 변경하거나 삭제하지 않으며 다시 연결하려면 새 요청과 동의가 필요하다.
- 일반 구성원 제거는 계속 소유자 전용이다. 활성 가족 관계가 만든 멤버십은 한 방향만 제거할 수 없고 가족 관계 종료로 처리한다.
- 한 사용자는 여러 복약 공간의 서로 다른 역할을 가질 수 있다.
- 화면은 현재 선택한 기록 대상과 역할을 항상 식별할 수 있게 표시한다.
- 본인이 소유한 공간을 최초 기본값으로 선택하되 다른 공간으로 기록 대상을 바꾸는 것은 사용자의 명시적 동작이어야 한다. 알림 딥링크가 지정한 접근 가능 공간은 기본값보다 우선한다.

### 2.3 시간과 날짜

- DB의 순간 시각은 `timestamptz`로 저장한다.
- 화면 표시와 일별 조회 경계는 `Asia/Seoul`을 사용한다.
- 예정 시간과 실제 복용 시각을 분리한다.
- 일정은 매일 반복되는 한국 현지 `HH:mm` 설정이며 별도 예정 날짜를 저장하지 않는다. 일정 기록의 날짜별 분류는 실제 복용 시각 `taken_at`의 한국 날짜를 사용하고, 자정을 넘어 전날 일정으로 자동 귀속하지 않는다.
- 사용자가 P1에서 실제 시각을 수정해도 최초 생성 시각과 수정 시각은 유지한다.

### 2.4 저장 신뢰성

- 모든 생성·수정·삭제 요청은 완료까지 `await`한다.
- 저장 중에는 같은 제출 동작을 다시 실행할 수 없다.
- 같은 요청의 재시도는 한 건만 생성해야 한다.
- 중복 방지 범위는 `(care_space_id, client_request_id)`다. 같은 키를 다른 입력 내용에 재사용하면 새 내용이 저장된 것처럼 표시하지 않고, 기존 성공 행을 보여 주거나 충돌 오류를 표시한다.
- 성공 메시지는 DB 성공 응답 후 표시한다.
- 오류 메시지는 실패한 작업과 재시도 방법을 텍스트로 설명한다.

## 3. P0 요구사항

### 3.1 약과 일정 조회

- 선택한 복약 공간의 활성 약과 활성 일정을 Supabase에서 조회한다.
- 약에는 이름과 단위가 있다.
- 일정에는 약, 예정 현지 시각, 활성 상태가 있다.
- 홈과 투약 화면은 하드코딩된 약 목록이 아니라 조회 결과를 사용한다.

### 3.2 투약 기록 생성

필수 기록:

- 약
- 복용 수량
- 실제 복용 시각
- 중복 방지용 요청 ID
- 당시 약 이름과 단위

일정에서 시작한 경우 당시 예정 시각과 일정 연결 정보를 기록한다. 일정에 연결되지 않은 새 기록은 `schedule_id`가 없고 `is_extra = true`다. 기존 일정이 나중에 삭제되어 FK가 비워진 로그는 `is_extra = false`와 예정 시각 스냅샷을 유지하므로 `schedule_id is null`만으로 추가 복용을 판정하지 않는다.

홈은 `오늘 예정`을 첫 콘텐츠로 표시한 뒤 약별 빠른 기록, 오늘 상태, 복용기록 순서로 제공한다. 홈과 오늘 예정에서 일정 기록을 시작할 때는 예정 시각이 보이는 일정별 동작을 사용한다. 약 카드의 큰 동작이 아직 기록 없는 일정을 가리키면 그 예정 시각을 라벨에 포함하고, 그런 일정이 없을 때만 일정 없는 `추가 복용 기록`으로 제공한다. 현재 시각이나 수량만으로 일정을 자동 추론하지 않는다.

수량 버튼은 약의 `quantity_options`를 사용하고 직접 입력을 함께 제공한다. 선택지가 빈 약은 수량 대신 한 번의 복용 여부를 기록한다. 직접 입력은 유한한 숫자로 0보다 크고 1000 이하인 값만 저장한다.

### 3.3 오늘 상태 생성

기본 항목:

- 피로
- 근력
- 호흡
- 눈 증상
- 메모

복약 공간과 한국 날짜의 조합당 하루 한 건이며 같은 날짜에 다시 저장하면 별도 중복 행을 만들지 않는다.

새 상태 행에는 상태 선택 하나 이상 또는 비어 있지 않은 메모가 있어야 한다. 기존 행의 모든 내용을 지우려면 빈 행으로 저장하지 않고 명시적인 삭제 동작을 사용한다.

### 3.4 복용기록 확인

- 날짜별로 투약 기록을 조회한다.
- 약 이름, 실제 복용 시각, 수량, 메모를 표시한다.
- 삭제되지 않은 기록만 일반 화면에 표시한다.
- 일일 경계와 정렬은 한국 시간을 기준으로 한다.

### 3.5 오류와 빈 상태

다음 상태를 구분한다.

- 최초 로딩
- 데이터 없음
- 환경변수 설정 오류
- 네트워크 연결 실패
- Supabase 조회 실패
- 저장·수정·삭제 실패

오류 때문에 화면에 데이터가 없을 때 이를 “기록 없음”으로 오해하게 표현하지 않는다.

## 4. P1 요구사항

### 4.1 홈 정보

- 약별 마지막 실제 복용 시각과 수량
- 약별 오늘 누적 복용 수량
- 오늘 일정별 완료 상태의 `기록 있음`, 미완료 일정의 권한별 `기록하기` 동작과 전체 기록 건수

미완료 일정 카드에는 별도 상태 문구를 반복하지 않는다. `기록하기`는 입력 동작이며 미복용 판정이 아니다. 지각, 누락, 추가 복용을 자동 판정하지 않는다.

### 4.2 상세 투약 기록

- 사용자가 실제 복용 시각을 입력하거나 수정할 수 있다.
- 메모를 입력할 수 있다.
- 일정에서 시작한 복용과 일정 없는 추가 복용을 구분한다.
- 추가 복용을 입력해도 앱은 처방 적정성을 판단하지 않는다.

### 4.3 기록 수정과 삭제

- 수량, 실제 시각, 메모를 수정할 수 있다.
- 잘못 연결한 일정과 일정 없는 추가 복용 분류를 사용자가 명시적으로 정정할 수 있다. 이때만 선택한 일정의 예정 시각 스냅샷과 `is_extra`를 함께 갱신하고 `updated_at/updated_by`를 남긴다.
- 일정 설정 자체를 나중에 수정·삭제한 사실은 기존 로그의 스냅샷을 자동 변경하지 않는다. 삭제된 일정에 연결되었던 로그는 사용자가 새 분류를 명시적으로 선택하기 전까지 기존 분류와 예정 시각을 유지한다.
- 삭제는 즉시 물리 삭제하지 않고 `deleted_at`을 기록한다.
- 삭제 직후 실행 취소를 제공한다.
- 설정 변경과 기록 수정은 구분한다.

### 4.4 상태 수정과 삭제

- 날짜를 선택해 하루 상태를 조회한다.
- 기존 기록을 수정할 수 있다.
- 삭제 전 확인한다.

### 4.5 약과 스케줄 설정

- 소유자와 보호자 역할에 약·일정 설정 동작을 제공한다.
- 약 추가, 이름·단위·수량 선택지 수정, 활성/비활성화
- 약별로 여러 복용·알림 시간을 연속 추가하고 예정 시각을 수정하거나 각 시간을 끄기·켜기·삭제
- 등록 약 삭제는 확인 후 `deleted_at`을 기록하는 soft delete로 처리하고, 해당 약과 일정을 새 기록·알림 대상에서 제외한다.
- 약이나 복용·알림 시간을 삭제해도 기존 투약 로그를 연쇄 삭제하지 않고 기록 당시의 약 이름·단위·실제 복용 시각·수량 스냅샷을 유지한다.
- 변경된 설정은 새 기록에만 적용하고 과거 기록을 바꾸지 않는다.

### 4.6 날짜별 타임라인

- 선택한 한국 날짜의 투약 기록과 상태 기록을 함께 표시한다.
- 투약은 실제 시각 순으로 정렬하고, 각 항목에 기록 당시의 약 이름·실제 복용 시각·수량과 단위를 표시한다.
- 하루 상태는 해당 날짜의 별도 섹션으로 표시한다.
- 통계, 추이, 의학적 해석은 표시하지 않는다.

### 4.7 접근성

- 최소 터치 영역 48px
- 시스템 글자 확대 대응
- 키보드만으로 모든 기능 사용 가능
- 화면 낭독기용 이름·상태·오류 연결
- 색상 외 텍스트로 상태 표현
- 저장 중과 비활성 상태를 보조기술에 전달

### 4.8 투약 일정 알림

- 로그인한 구성원은 환경설정 화면에서 접근 가능한 각 복약 공간의 현재 기기 알림을 개별적으로 `켜기 / 테스트 / 끄기` 할 수 있다.
- 알림 권한과 Push 구독은 브라우저가 기기별로 관리하고 사용자·복약 공간에 연결한다. 다른 공간 또는 다른 사용자의 구독으로 간주하지 않는다.
- 같은 브라우저 구독을 여러 접근 가능한 복약 공간에 각각 opt-in할 수 있으며 한 공간의 알림을 꺼도 다른 공간의 대상 연결은 유지한다.
- 가족 기록 관리 요청 수락이나 기존 관계의 양방향 전환만으로 알림을 자동 활성화하지 않는다.
- 알림 발송 대상은 활성 약에 등록한 여러 활성 복용·알림 시간이다.
- 예정 시각부터 해당 한국 날짜가 끝나기 전까지 같은 일정의 삭제되지 않은 투약 기록이 없으면 5분 간격으로 알림 발송을 시도한다.
- 같은 일정의 투약 기록이 생기거나 일정·약을 끄거나 일정을 삭제하면 새 반복 알림을 만들지 않는다. 서버가 이미 점유한 건도 외부 발송 직전에 다시 확인해 유효하지 않으면 `skipped` 처리한다.
- Supabase Cron은 매분 발송 대상을 확인하고, Vercel의 보호된 발송 API가 Web Push 전송을 수행한다.
- 같은 기기·일정·5분 알림 회차의 발송은 한 번만 생성한다.
- 반복 알림은 서비스 워커가 같은 일정의 이전 표시를 먼저 닫고 새 알림과 진동을 요청해, 브라우저의 같은 tag 교체 무음 경로를 피하면서 알림 항목이 계속 쌓이지 않게 한다.
- 같은 일정·한국 날짜의 Web Push topic을 재사용한다. 일정 알림은 TTL 0으로 즉시 전달만 요청해 투약 기록이나 일정 변경 뒤 대기 중이던 알림이 늦게 표시될 가능성을 줄인다.
- 현재 기기에서 일정 투약 기록을 저장하거나 시간을 끄거나 삭제하면 표시 중인 같은 일정 알림을 닫는다.
- 알림 제목과 본문에 예정 시각과 약 이름을 포함하고, Android가 지원하면 단색 캡슐 badge를 표시한다. payload 문구에는 프로젝트명을 넣지 않는다.
- 알림을 눌러 앱으로 들어오면 클릭한 알림과 같은 일정의 남은 표시를 닫고 다른 약의 알림은 유지한다.
- 알림을 누르면 해당 약과 일정이 선택된 투약 기록 화면으로 이동한다.
- iPhone/iPad에서는 iOS/iPadOS 16.4 이상에서 Safari의 `홈 화면에 추가`로 설치한 앱을 열어 알림을 허용한다.
- 권한 요청은 사용자가 알림 켜기 버튼을 누른 동작 안에서만 시작한다.
- 알림 문구는 기록 확인을 안내할 뿐 미복용, 지연, 추가 복용 필요를 판단하거나 지시하지 않는다.
- 네트워크, 운영체제의 집중 모드·절전 설정과 푸시 서비스 상태에 따라 알림이 늦거나 도착하지 않을 수 있음을 설정 화면에 표시한다.
- 발송 직전에도 구독 소유자에게 해당 복약 공간의 구성원 권한이 있는지 확인하며, 탈퇴·권한 회수 후에는 새 알림을 보내지 않는다.

## 6. P0 수용 기준

- 빈 Supabase 설정으로 운영 모드를 실행하면 설정 오류가 보인다.
- 저장 실패 시 완료 메시지나 가짜 로컬 기록이 남지 않는다.
- 제출 버튼 연타와 동일 요청 재시도로 투약 로그가 하나만 생긴다.
- 같은 `(care_space_id, client_request_id)`를 다른 내용으로 재사용해도 새 내용이 저장된 것처럼 표시되지 않는다.
- 상태 선택과 메모가 모두 비어 있는 새 상태 행이 저장되지 않는다.
- 자정 전후 기록이 한국 날짜에 맞게 조회된다.
- 약이나 일정 설정을 바꿔도 기존 로그의 표시 정보가 달라지지 않는다.
- 서로 구성원이 아닌 두 사용자는 상대 복약 공간의 데이터와 구성원 정보를 조회하거나 변경할 수 없다.
- 보호자는 약·일정·로그·상태를 변경할 수 있지만 공간 이름·구성원·초대 변경은 거부되고, 조회자는 모든 변경이 거부된다.
- 확인된 이메일과 일치하는 수신자가 자기 소유 공간을 선택하고 양방향 권한에 명시적으로 동의한 경우에만 요청자와 수신자가 각각 상대 공간의 보호자가 된다.
- 기존 단방향 관계는 양쪽 화면에 실제 접근 방향으로 표시되고 반대 방향 멤버십이 자동 생성되지 않는다. 현재 상대 기록을 관리하는 참여자의 별도 공간 선택·동의로만 양방향 전환된다.
- 관계 참여자는 어느 쪽이든 관계를 종료할 수 있다. 양방향 관계는 두 접근을 함께 제거하고 단방향 관계는 기존 접근만 제거하며, 관계와 건강 기록은 삭제되지 않는다.
- Playwright는 실제 Supabase 없이 메모리 mock DB로 핵심 흐름을 검증한다.
