# 보안과 개인정보

## 1. 확정된 접근 모델

이 앱은 로그인, 접근 코드, 기기 승인을 사용하지 않는다. 가족은 같은 Vercel URL에 직접 접속하고 하나의 Supabase 데이터셋을 함께 사용한다.

따라서 다음 제약을 명확히 받아들인다.

- URL을 아는 사람은 데이터를 조회하거나 변경할 수 있다.
- URL 자체는 비밀번호나 접근 제어가 아니다.
- 가족 구성원을 식별하거나 기기별 권한을 회수할 수 없다.
- 사용자별 데이터 분리와 감사는 제공하지 않는다.

이 접근 모델은 소규모 가족용이라는 현재 범위에서 확정된 결정이다. 보안 문서가 이를 인증된 서비스처럼 표현해서는 안 된다.

## 2. Supabase 공개 키

클라이언트에는 다음만 사용할 수 있다.

- `NEXT_PUBLIC_SUPABASE_URL`
- `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`
- 호환이 필요한 경우 `NEXT_PUBLIC_SUPABASE_ANON_KEY`

publishable/anon key는 브라우저에 공개되는 키다. `service_role`, `sb_secret_...` 등 비밀 키는 코드, `.env.example`, GitHub Actions, Vercel의 `NEXT_PUBLIC_*` 변수에 넣지 않는다.

운영 모드에서 URL 또는 공개 키가 없거나 비밀 키 형식이 들어오면 앱은 Supabase 클라이언트를 만들지 않고 설정 오류를 표시한다.

## 3. RLS의 역할과 한계

모든 공개 테이블에 RLS를 활성화하고 anon 역할에 필요한 연산만 명시적으로 허용한다.

그러나 인증이 없으므로 RLS는 가족 구성원을 서로 구분하지 못한다. 이 프로젝트에서 RLS의 목적은 다음으로 제한된다.

- 노출할 테이블과 연산을 명시한다.
- DB check, FK, trigger와 함께 잘못된 데이터 형태를 차단한다.
- 사용하지 않는 스키마나 테이블에 anon 접근을 주지 않는다.

P1에서 약·일정 설정과 기록 수정·삭제를 지원하므로 해당 기능을 쓰는 모든 URL 방문자도 같은 연산 권한을 가진다. 사용자별 `auth.uid()` 격리를 제공한다고 주장하지 않는다.

테이블마다 `select`, `insert`, `update`, `delete` 정책을 개별 검토한다. 정책 테스트는 허용 동작뿐 아니라 허용하지 않은 테이블·연산이 거부되는지도 확인한다.

## 4. DB가 보장할 규칙

클라이언트 입력만 신뢰하지 않는다.

- 중복 방지용 `client_request_id` unique
- 수량 양수 check
- 상태 날짜 unique
- 약·일정 FK
- 로그 스냅샷을 DB trigger로 생성
- `updated_at`을 DB trigger로 갱신
- 과거 로그를 연쇄 삭제하지 않는 FK 정책

로그의 약 이름·단위·일정 시각 스냅샷은 클라이언트가 임의로 정하는 값이 아니라 insert 시 DB가 현재 설정에서 복사한다.

## 5. 브라우저 데이터

- 앱 데이터는 React 메모리와 화면 상태에만 일시적으로 존재할 수 있다.
- localStorage, IndexedDB, Cache Storage, 쿠키에 건강 기록을 저장하지 않는다.
- 서비스 워커로 화면이나 API 응답을 오프라인 캐시하지 않는다.
- 네트워크 요청 실패 내용을 큐에 보관하지 않는다.
- 페이지 새로고침 후 데이터는 Supabase에서 다시 조회한다.

Playwright mock DB도 테스트 프로세스의 메모리에만 존재하고 실제 Supabase나 브라우저 영구 저장소를 사용하지 않는다.

## 6. 개인정보 최소화

저장 대상은 약 설정, 복용 기록, 상태 선택, 사용자가 작성한 메모로 제한한다.

- 이름, 주민등록번호, 주소, 전화번호를 요구하지 않는다.
- 메모에 불필요한 식별정보를 쓰지 않도록 안내한다.
- 오류·분석 로그에 약 메모나 상태 내용을 보내지 않는다.
- 브라우저 콘솔에 Supabase 응답 전체나 환경변수를 출력하지 않는다.
- 화면 공유·공용 기기 사용 시 건강 기록이 노출될 수 있음을 운영자가 이해해야 한다.

## 7. URL과 운영

- 저장소 링크와 배포 URL을 문서 예시 외에 공개 채널에 게시하지 않는다.
- URL 유출은 곧 데이터 접근 가능성을 뜻하지만 URL 회전만으로 기존 접근을 확실히 회수할 수 있다고 보지 않는다.
- 접근 제어가 필요한 사용 방식으로 확대하려면 현재 확정 범위를 다시 결정해야 한다.

## 8. 제외 보안 기능

- 로그인과 세션
- 접근 코드
- 기기 승인·차단
- 사용자별 RLS
- 역할별 권한
- 초대와 공유 관리
- 로컬 암호화 저장소
- 백업·복원

이 항목들은 P0/P1의 미완료 TODO가 아니라 명시적으로 제외된 기능이다.
