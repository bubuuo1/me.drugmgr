# 모바일 PWA, Web Push와 온라인 전용 정책

> 이 문서는 온라인 전용 런타임, 서비스 워커와 Web Push 동작의 정본이다. 알림 UI는 [03 UI 및 접근성](03-ui.md), private 테이블과 RPC는 [06 데이터베이스](06-database.md)를 따른다.

## 1. 목표

휴대폰에서 URL을 열거나 홈 화면 바로가기로 실행하고 Google 로그인 후 빠르게 기록하며, 사용자가 직접 선택한 복약 공간과 기기에는 투약 일정 Web Push를 보낸다. 설치형 외형과 푸시 서비스 워커는 편의를 위한 것이며 오프라인 앱을 의미하지 않는다.

## 2. 플랫폼

- Next.js
- React
- TypeScript
- Supabase
- Vercel
- 모바일 세로 화면 우선

최소 확인 환경:

- Android Chrome
- iOS/iPadOS 16.4 이상 Safari와 홈 화면에 추가한 앱
- 데스크톱 Chromium 기반 Playwright

## 3. 홈 화면 실행

manifest, 아이콘, 모바일 viewport, theme color, standalone 표시를 제공한다. 홈 화면 아이콘이나 브라우저 바로가기로 실행하면 첫 화면을 연다.

보호된 화면은 Google 로그인이 필요하다. 로그인 세션이 없거나 만료되면 로그인 화면으로 이동하고, 인증 callback은 허용된 앱 내부 경로로만 복귀한다.

iPhone/iPad에서 알림을 사용하려면 Safari 공유 메뉴에서 `홈 화면에 추가`한 뒤 그 아이콘으로 앱을 열어야 한다. 홈 화면 추가는 알림 사용을 위한 플랫폼 절차이며 앱의 승인 기기 등록이 아니다.

## 4. 온라인 전용

모든 조회와 저장은 Supabase 연결이 필요하다.

- 온라인이 아니거나 Supabase 요청이 실패하면 오류를 표시한다.
- 저장 실패를 완료로 표시하지 않는다.
- 네트워크가 돌아오면 사용자가 다시 시도하거나 화면이 최신 데이터를 다시 조회한다.
- 실패한 쓰기 요청을 나중에 자동 전송하지 않는다.
- 이전에 조회한 데이터를 영구 캐시해 오프라인 화면으로 제공하지 않는다.

`navigator.onLine`은 보조 신호일 뿐 저장 성공 근거가 아니다. 실제 Supabase 요청 결과를 기준으로 성공·실패를 판단한다.

## 5. 사용하지 않는 웹 저장 기능

다음은 사용하지 않는다.

- localStorage
- IndexedDB
- 건강 기록을 담는 앱 데이터용 쿠키(인증 세션 쿠키는 예외)
- Cache Storage의 앱/API 데이터 캐시
- 오프라인 작업 큐
- 백그라운드 동기화
- 브라우저와 서버 간 충돌 병합

푸시 알림을 위해 `/sw.js` 서비스 워커를 등록한다. 이 서비스 워커의 알림 동작은 `push`와 `notificationclick`에서만 수행하고 `fetch` 핸들러나 앱/API 캐시를 두지 않는다. 설치·활성화할 때 이전 `medicine-app-*` 캐시가 있으면 정리한다.

브라우저가 관리하는 인증 세션 쿠키, 서비스 워커, 알림 권한과 Push 구독은 건강 기록의 로컬 저장이 아니다. 투약·상태·설정 데이터의 유일한 영구 저장소는 계속 Supabase다.

## 6. 투약 일정 Web Push — P1

### 6.1 기기 설정

- 로그인한 구성원이 복약 공간을 선택하고 `이 기기에서 이 공간 알림 받기`를 눌렀을 때만 권한을 요청한다.
- 구독 후 `테스트 알림`으로 현재 기기의 수신 경로를 확인할 수 있다.
- `이 공간 알림 끄기`는 현재 사용자·브라우저 구독과 해당 복약 공간의 대상 연결만 제거한다. 다른 공간 대상이 남아 있으면 브라우저 구독 자체는 유지한다.
- 권한과 구독은 브라우저가 기기별로 관리한다. 가족 기록 관리 요청 수락이나 기존 관계의 양방향 전환은 알림을 자동 활성화하지 않으며 구독은 기기 승인을 대체하지 않는다.
- 같은 사용자는 한 기기에서 여러 접근 가능한 복약 공간을 각각 opt-in할 수 있다.
- 조회자도 본인 기기의 알림을 켜고 끌 수 있지만 투약 기록을 만들 수는 없다. 조회자가 알림을 눌렀을 때는 읽기 전용 권한을 유지하며 복용을 지시하는 문구나 사용할 수 없는 기록 동작을 제공하지 않는다.

### 6.2 일정 발송 흐름

1. Supabase Cron이 매분 Vault에 보관한 URL과 비밀값으로 Vercel 발송 API를 호출한다.
2. 서버는 사용자·기기 구독에 연결된 복약 공간의 약별 활성 복용·알림 시간마다 예정 시각부터 5분 간격으로 계산한 최신 한국 시각 알림 회차를 확인한다.
3. 가족 관계 종료 등으로 구성원 권한이 없거나 같은 공간·한국 날짜·일정의 삭제되지 않은 투약 기록이 있거나 일정·약·구독이 비활성이면 새 회차를 만들지 않고, 아직 전송되지 않은 회차는 `skipped` 처리한다.
4. 기기·공간·일정·5분 회차 unique 제약으로 같은 알림 회차의 중복 생성을 막는다.
5. Vercel API는 Web Push 직전에 공간 멤버십을 포함한 같은 조건을 다시 확인해 유효한 회차만 VAPID로 전송하고 접수·실패 결과를 Supabase에 기록한다.
6. 일정 기록 저장·끄기·삭제 시 현재 기기에 표시된 같은 일정 알림을 닫는다.
7. 사용자가 알림을 누르면 해당 복약 공간, 약과 일정이 선택된 투약 기록 화면을 연다.

투약 기록이 없는 동안의 5분 간격 새 알림과 전송 실패 재시도는 별도로 처리한다. 요청 중단이나 일시 실패는 각 회차부터 5분 이내에 최대 3회까지 같은 delivery를 다시 시도한다. 시도 번호를 확인해 늦게 도착한 이전 요청이 새 결과를 덮어쓰지 않게 한다.

같은 일정과 한국 날짜의 반복 알림은 동일한 논리 식별자를 사용한다. 서비스 워커는 기존 표시를 먼저 닫고 tag 없는 새 알림과 명시적인 진동 패턴을 요청한다. 따라서 같은 tag 교체가 무음 처리되는 경로를 피하면서 화면에는 같은 일정 알림 하나만 남긴다. Android 알림 표시용 `badge`에는 96px 단색 캡슐 아이콘을 지정한다. Web Push topic도 같은 논리 식별자의 해시를 사용하고 일정 알림은 TTL 0으로 즉시 전달만 요청한다. 운영체제의 무음·집중 모드와 플랫폼 지원에 따라 실제 진동·아이콘 표시 여부는 달라질 수 있다.

알림 제목과 본문에는 예정 시각과 약 이름을 함께 표시해 어떤 약의 기록인지 바로 구분한다. 프로젝트명은 payload 문구에 넣지 않는다. 운영체제가 보안상 자동 표시하는 설치 앱 이름이나 사이트 출처는 웹 코드에서 숨길 수 없다. 알림을 누르면 클릭한 알림과 같은 일정의 남은 표시를 닫고 기록 화면을 연다. 다른 약의 알림은 유지한다. 알림 문구는 복용을 지시하거나 미복용·지연을 판정하지 않는다.

### 6.3 전달 한계

push service가 발송 요청을 접수해도 기기에 정시에 표시되는 것은 보장되지 않는다. 네트워크, 브라우저, 운영체제의 집중 모드·절전 설정에 따라 늦게 도착하거나 도착하지 않을 수 있다. 외부 push service가 이미 즉시 전달을 시작한 마지막 한 건은 서버에서 회수할 수 없지만, TTL 0으로 서버 대기열에 남겨 두지는 않는다. 설정 화면에 이 한계를 항상 표시하고 알림 수신 여부를 복용 기록으로 사용하지 않는다.

## 7. 연결 상태 UI

- 연결이 끊긴 것이 확인되면 “인터넷 연결이 필요합니다.”를 표시한다.
- 저장 버튼은 요청 불가능한 상태임을 텍스트와 비활성 상태로 전달한다.
- 조회 실패와 정상적인 빈 기록을 구분한다.
- 자동 저장이나 실패한 쓰기의 나중 자동 재전송을 약속하지 않는다.
- 다시 연결된 뒤 재조회 중 상태를 표시한다.

## 8. 다기기 최신성

각 기기는 로그인 사용자가 구성원인 복약 공간만 Supabase에서 읽는다. 같은 공간을 공유한 기기는 같은 최신 데이터를 본다.

- 쓰기 성공 후 DB가 반환한 최신 행을 현재 화면에 반영하고 파생 정보를 다시 계산한다. 여러 행이 함께 바뀌는 작업은 관련 범위를 다시 조회한다.
- 복약 공간을 전환할 때 이전 공간의 화면 데이터를 먼저 비우고 새 공간만 조회한다.
- 화면 진입, 날짜 변경, 앱 포커스·표시 상태 복귀 시 최신 데이터를 조회한다.
- 화면이 계속 보일 때는 60초마다 접근 가능한 공간·대기 초대를 경량 확인한다. 가족 화면에서는 현재 공간의 구성원·요청·관계도 함께 확인한다.
- 화면이 계속 보일 때 5분마다 현재 공간의 약·일정·기록·상태를 안전 재조회한다. 재조회 중에는 최초 로딩 화면으로 바꾸지 않고 실제 구조가 달라진 상태만 교체한다.
- 일반 Postgres Changes publication은 DELETE 이벤트에 RLS가 적용되지 않으므로 건강정보 테이블에 사용하지 않는다. 향후 실시간 무효화가 필요하면 사용자별 private Broadcast와 관계 종료 검증을 별도 설계한다.
- 다른 기기의 변경을 로컬 데이터와 병합하지 않는다.

## 9. 터치와 화면

- 세로 화면과 최대 폭 28rem을 기본으로 한다.
- 주요 터치 영역은 64~72px, 최소 터치 영역은 48px다.
- 작은 아이콘이나 작은 텍스트만을 주요 동작으로 쓰지 않는다.
- safe area와 소프트 키보드를 고려한다.
- 가로 화면 전용 레이아웃은 제공하지 않지만 핵심 동작이 막히면 안 된다.

## 10. 제외 기능

- 오프라인 첫 화면과 최근 데이터
- 오프라인 투약·상태 기록
- 오프라인 실패 쓰기 큐의 자동 재전송과 충돌 병합
- 백업·복원
- 앱 자체의 승인 기기 목록·차단 관리
- 알림의 정시·필수 도착 보장과 미복용·지연 판정
